## Что собирается

```bash
pnpm run build
```

За этим стоит `pnpm -r --workspace-concurrency=1 run build`, то есть пакеты собираются **по одному**, а не параллельно. Параллельно две Nuxt-сборки и webpack-бандл съедали память и падали на слабых машинах.

| Пакет | Чем собирается | Результат |
| --- | --- | --- |
| `unicore-common` | tsup | `dist` в CJS и ESM с типами |
| `unicore-server` | webpack + обфускатор | `dist/main.js`, `dist/cli/main.js` |
| `unicore-client` | Nuxt | `.output` |
| `unicore-admin` | Nuxt | `.output` |

Общий пакет всегда идёт первым: остальные без него не соберутся.

В ветке разработки после `unicore-common` собирается `unicore-api`. Его сборщик
проверяет публичные доверенные ключи и создаёт обфусцированный SDK лицензирования.
Поставляемый архив содержит готовый SDK; читаемая папка `workspaces/api/licensing-src`
в него не включается. При повторной сборке такого архива проверяются состав SDK и
контрольные суммы.

## Проверки качества

Для разработки используйте актуальную Node 22 начиная с 22.13 либо Node 24.
Минимальная версия Node для самой CMS остаётся 22.12. Новые инструменты качества
изолированы от зависимостей работающего сайта:

```bash
pnpm quality:install
pnpm lint
pnpm format:check
```

ESLint проверяет поддерживаемые файлы лицензирования из `.quality-scope.json`,
новые файлы и изменения в индексе Git. В CI к ним добавляется diff относительно
базового коммита. Для критичных TypeScript-файлов включены проверки забытых и
неверно использованных Promise.

Prettier проверяет новые файлы и поддерживаемый список. В старых файлах вне этого
списка он проверяет изменения, если прежняя версия уже соответствовала формату;
остальные отмечает как старое форматирование вне объёма проверки. Это постепенное
подключение проверок, а не утверждение, что весь прежний код CMS прошёл линтер.
У backend сохраняется его существующая конфигурация Prettier.

CI запускает эти команды после сборки на Node 22 и 24. Сборка API также проверяет
публичный контракт. Для изменения экспортов обновите снимок осознанно и приложите
соответствующую версию API.

<Callout type="warn" title="Погасите dev-серверы">
Если параллельно крутится `pnpm run dev`, сборка фронтов падает на блокировке файлов в `.nuxt`. Сначала остановить.
</Callout>

## Сервер: webpack и обфускация

Сервер собирается в один бандл, а не в дерево файлов. После сборки бандл прогоняется через `javascript-obfuscator`.

Отключается переменной:

```bash
OBFUSCATE=0 pnpm run build:server
```

Полезно, когда нужно прочитать стектрейс: в обфусцированном бандле он бесполезен.

<Callout type="error" title="Обфускация запускается отдельными процессами">
Иначе Node падал с кодом 134 — V8 упирался в лимит кучи и делал abort. Каждый бандл обфусцируется в собственном процессе; это заметно на игровых панелях вроде Pterodactyl, где памяти мало.
</Callout>

И ещё: `transpileOnly` в ts-loader включать нельзя. Он выбрасывает метаданные типов, а на них держатся декораторы TypeORM. Сущности перестают собираться в схему, и приложение падает уже в рантайме.

## Запуск

```bash
pnpm run start
```

Поднимает три процесса разом. На проде удобнее pm2, конфиг для него уже лежит в корне:

```bash
pm2 start ecosystem.config.js
pm2 save
pm2 startup
```

Фронты стартуют не напрямую через Nuxt, а через `start.mjs`. Он читает порт тем же кодом, что и сервер (`unicore-common/ports`), и прокидывает публичные переменные в окружение Nitro. Так порт из `.env` побеждает то, что подсунула игровая панель.

## Прокси

Приложения слушают три порта и ничего не знают про HTTPS. Сертификаты вешайте на прокси.

```nginx
server {
    server_name example.com;
    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Аналогично для `admin.example.com` → `:4000` и `api.example.com` → `:5000`.

<Callout type="error" title="Не забудьте `TRUST_PROXY`">
Если в `.env` нет `TRUST_PROXY`, сервер у всех клиентов увидит IP прокси. Отвалятся вебхуки платёжек, IP-фильтр API-ключей и антифлуд. Для одного nginx ставьте `1` или `loopback`.
</Callout>

Вебсокетам нужен апгрейд соединения:

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
```

Без него онлайн серверов не будет обновляться в реальном времени.

## Docker

`docker-compose.yml` описывает четыре сервиса с профилями:

| Профиль | Сервис |
| --- | --- |
| `prod` | Приложение, все три процесса в одном контейнере |
| `nginx` | Прокси с доменами из `CLIENT_HOST`, `ADMIN_HOST`, `SERVER_HOST` |
| `dev` | phpMyAdmin на `:8081` |

MariaDB поднимается всегда. Образ двухстадийный: сборка идёт на `node:22-bookworm-slim`, рантайм собран на том же slim плюс `tini` и системные библиотеки для рендера скинов.

Наружу смонтированы `storage` и `logs`, их надо бэкапить с хоста.

## CI

GitHub Actions собирает проект на Node 22 и 24, потом гоняет проверку типов по всем трём пакетам. Артефакт собирается на Node 22, `node_modules` и промежуточные папки сборки из него выкинуты.

Проверка типов ловит не всё. Например, ни `pnpm run build`, ни `typecheck` не видят проблем с именованными импортами CJS-пакетов: те падают только при запуске собранного SSR. После правок в плагинах фронта запустите `.output/server/index.mjs` и дёрните пару страниц.

## Обновление на проде

Полный порядок описан на [странице обновления](/docs/start/update). Коротко: бэкап → `git pull` → `pnpm install` → `pnpm run build` → перезапуск. Схему сервер приведёт в порядок сам при старте.
