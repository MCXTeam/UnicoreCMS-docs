## Подключение

Настройки собираются в `src/ormconfig.ts` из `envConfig`, напрямую из `process.env` не читается ничего. Тип базы берётся из `DATABASE_TYPE`: `mysql`, `mariadb` или `postgres`.

Списка сущностей нигде нет. При сборке webpack собирает все файлы `*.entity.ts` через `require.context`, при запуске из `dist` берётся маска `*.entity.js`. Новая сущность подхватывается сама, регистрировать её где-то ещё не нужно.

## Именование

Имена в базе задаёт своя `NamingStrategy`. Правила такие:

| Что | Правило | Пример |
| --- | --- | --- |
| Таблица | `unicore_` + snake_case во множественном числе | `News` → `unicore_news` |
| Колонка | snake_case | `shortDescription` → `short_description` |
| Join-колонка | `отношение_ссылка` | `server` + `id` → `server_id` |

Явное имя в декораторе всегда побеждает автоматику. В проекте его почти везде проставили руками, чтобы рефакторинг не преподносил сюрпризов.

## Транзакции

Подключён `typeorm-transactional`. Метод, помеченный `@Transactional()`, выполняется в одной транзакции вместе со всем, что он вызовет вглубь. Прокидывать `EntityManager` через параметры не нужно.

Инициализируется всё в `main.ts` до создания приложения:

```ts
initializeTransactionalContext()
```

## Время

За время отвечает одна ручка, `TIMEZONE` в `.env`. Дальше происходит вот что:

1. `process.env.TZ` выставляется в самом начале `main.ts`, до всего остального.
2. В настройки подключения уходит смещение этой зоны.
3. Для MySQL и MariaDB на каждое соединение в пуле выполняется `SET time_zone`.

<Callout title="Зачем `SET time_zone` на каждое соединение">
Колонки с `CURRENT_TIMESTAMP` заполняет сама база, а не Node. Если не выставить зону на сессии, MySQL пишет время по своей системной зоне, и записи получают чужие метки. Приложение об этом не узнает.
</Callout>

На фронте эта же зона идёт в форматирование дат. И не вызывайте `.local()` в шаблонах: он переведёт время в зону браузера, и оно разъедется с тем, что показывает админка.

## Схема базы

Схему приводит в порядок сам сервер при старте — до того, как начнёт принимать запросы. Отдельной команды для боевой установки нет.

Порядок такой:

1. Берётся блокировка базы, чтобы под pm2 в кластере или в нескольких контейнерах этим занимался один процесс.
2. Применяются изменения, которых нет в журнале `unicore_migrations`.
3. Досоздаётся то, что есть в сущностях, но отсутствует в базе: таблицы, колонки, индексы, в том числе у расширений.

Третий шаг **только добавляет**. `DROP` любого вида, удаление колонок и смена типов пропускаются, а их количество печатается в лог с подсказкой посмотреть подробности через `pnpm run align`.

### Как писать изменения схемы

Структурные правки (новая таблица, колонка, индекс) обычно не требуют ничего: досоздание подхватит их само. Миграция нужна там, где двигаются данные или что-то удаляется — переименование колонки, смена типа с конверсией, чистка мусора.

Файл кладётся в `src/migrations/steps/<timestamp>-<имя>.migration.ts`, имя класса заканчивается тем же timestamp — по нему определяется порядок.

```ts
export class RenameSlogan1756000000000 implements MigrationInterface {
  name = 'RenameSlogan1756000000000';

  public async up(queryRunner: QueryRunner): Promise<void> {
    const table = await queryRunner.getTable('unicore_servers');
    const column = table?.findColumnByName('slogan');

    if (!column) return;

    await queryRunner.renameColumn(table, column, 'tagline');
  }

  public async down(): Promise<void> {}
}
```

Два правила, которые экономят ночи:

- **Идемпотентность.** Начинайте с проверки состояния (`getTable`, `findColumnByName`, текущий тип). Установки в дикой природе разные: где-то правка уже сделана руками, где-то нет.
- **Мелкие шаги.** MySQL не откатывает DDL: миграция, упавшая на середине, оставит схему в промежуточном состоянии. Чем меньше шаг, тем понятнее, где чинить.

Пишите через API `QueryRunner`, а не сырым SQL: проект поддерживает MySQL, MariaDB и PostgreSQL, и синтаксис у них разный.

<Callout type="error" title="Смена типа колонки первичного ключа">
Если поменять длину или тип колонки, входящей в первичный ключ, TypeORM вместо `ALTER TABLE` может **дропнуть колонку и создать заново**, вместе с данными и самим первичным ключом. В истории проекта такое уже было: изменение `varchar` у кода языка снесло колонку `code` в таблице языков.

Именно поэтому досоздание схемы такие изменения не выполняет, а сообщает о них. Правки первичных ключей делайте миграцией и сначала прогоняйте на копии боевой базы.
</Callout>

### Команды для разработки

| Команда | Что делает |
| --- | --- |
| `pnpm run migrate:status` | Журнал: что применено, есть ли ожидающие |
| `pnpm run align` | Досоздать недостающее, не запуская сервер |
| `pnpm run sync` | Полная синхронизация TypeORM, умеет удалять колонки — только для локальной базы |

## Полезно знать

**Не фильтруйте по объекту сущности целиком.** В TypeORM 0.3 это разворачивается в сравнение кортежа колонок и падает с `ER_OPERAND_COLUMNS`:

```ts
find({ where: { user } })          // ошибка
find({ where: { user: { uuid } } })  // правильно
```

**`findOne` требует `where`.** Вызов без него в 0.3 бросает исключение, а не возвращает первую запись, как было в 0.2.

**Спред ломает переводы.** Интерсептор локализации ищет переводимые сущности по их классу. Если сервис вернёт `{ ...entity, extra: 1 }`, класс потеряется и переводы не подставятся. Нужно добавить поле — берите `Object.assign(entity, { extra: 1 })`.

## Шифрованные колонки

Часть полей лежит в базе зашифрованной, ключ берётся из `ENCRYPTION_KEY` в `.env`:

| Поле | Где |
| --- | --- |
| Хеш пароля | `unicore_users.password` |
| Секрет 2FA | `unicore_users.two_factor_secret` |
| Пароль RCON | `unicore_rcons.password` |

Работает это через трансформер колонки: сервис видит обычную строку, а шифруется всё на границе с базой. Внутри обёртки лежит не голый пароль, а уже argon2id-хеш. Шифрование добавили сверху, чтобы утёкший дамп сам по себе ничего не давал.

Ключ меняет команда `crypto-rewrap`, см. [страницу про `.env`](/docs/start/env).
