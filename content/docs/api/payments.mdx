## Как выглядит платёж

<Steps>
<Step>

### Игрок жмёт «Пополнить»

Фронт дёргает ручку выбранного провайдера:

```http
POST /payment/methods/unitpay/link
Authorization: Bearer <accessToken>

{ "amount": 500 }
```

Сервер создаёт счёт со статусом `waiting`, подписывает параметры своим ключом и возвращает ссылку:

```json
{ "link": "https://unitpay.ru/pay/…?sum=500&account=1234&sign=…" }
```

</Step>

<Step>

### Игрок платит на стороне агрегатора

Мы в этом не участвуем. Карта, СБП, кошелёк остаются на стороне провайдера.

</Step>

<Step>

### Агрегатор шлёт уведомление

```http
POST /payment/methods/unitpay/handler
```

Ручка публичная, авторизации у агрегатора нет и быть не может. Вместо неё работают две проверки.

</Step>

<Step>

### Игрок возвращается на сайт

```
/payment/redirect/success/unitpay
/payment/redirect/fail/unitpay
```

Обе ручки просто редиректят на страницу оплаты сайта с параметрами статуса. Баланс к этому моменту уже пополнен уведомлением, а не редиректом. Если игрок закрыл вкладку, редиректа не будет вовсе, а деньги всё равно дойдут.

</Step>
</Steps>

## Что проверяется в уведомлении

**IP отправителя.** У каждого провайдера захардкожен список его адресов. Запрос с чужого адреса отклоняется до всех остальных проверок.

**Подпись.** Сервер пересчитывает параметры с секретным ключом из `.env` и сверяет результат с присланной подписью. Не сошлось — отказ.

Только после обеих проверок счёт помечается оплаченным.

<Callout title="Двойное уведомление ничего не сломает">
Смена статуса делается условным `UPDATE ... WHERE status = 'waiting'`. Если агрегатор пришлёт подтверждение дважды, второй запрос не изменит ни одной строки, и баланс не пополнится второй раз.
</Callout>

## Что отвечает наша сторона

Формат ответа зависит от провайдера, каждый ждёт своё. Общая логика такая:

| Ситуация | Что вернётся |
| --- | --- |
| Всё хорошо | `OK` |
| IP не из списка провайдера | `bad ip!` |
| Подпись не сошлась | `wrong sign!` |
| Счёта нет или он уже оплачен | `wrong payment id!` |

Эти строки видно в логах вебхуков у агрегатора, по ним и разбираются с проблемой.

## Отладка

Симптом почти всегда один. У агрегатора платёж прошёл, а на сайте баланс не изменился. Дальше по списку.

<Accordions>
<Accordion title="В логах агрегатора — bad ip">

Сервер видит не тот IP, что отправил запрос. Чаще всего виноват прокси без `TRUST_PROXY` в `.env`: тогда у всех запросов будет IP вашего nginx.

Посмотрите в логах сервера, с какого адреса пришёл запрос. Увидели `127.0.0.1` или адрес контейнера, значит дело в этом.

</Accordion>
<Accordion title="В логах агрегатора — wrong sign">

Не тот секретный ключ. У FreeKassa и Enot.io ключей два: первый подписывает ссылку, второй проверяет уведомление. Если перепутать их местами, получится ровно это: ссылка создаётся нормально, а подтверждение не проходит.

</Accordion>
<Accordion title="Уведомление вообще не приходит">

Адрес недоступен снаружи. Проверьте руками:

```bash
curl -X POST https://api.example.com/payment/methods/unitpay/handler
```

Любой ответ, кроме таймаута и 404, означает, что ручка видна снаружи. Чаще всего уведомления просто настроены на адрес сайта, а не API.

</Accordion>
<Accordion title="Всё прошло, но бонус не начислен">

Бонус за пополнение считается процентом от суммы по самому высокому порогу, который платёж перешагнул. Платёж на 499 при пороге 500 бонуса не даст. Пороги настраиваются в **E-Commerce → Пополнение**.

</Accordion>
</Accordions>

## Свой провайдер

Все реализации лежат в `src/payment/methods/<провайдер>` и устроены одинаково:

```ts
export class MyPayService implements PaymentCoreService {
  async createLink(user, input, ip): Promise<PaymentLink> {
    const payment = await this.paymentHandler.create(MyPayModule.id, input.amount, user, ip)
    return { link: '…' }
  }

  async handler(ip, input): Promise<any> {
    // проверить IP и подпись
    await this.paymentHandler.handler(input.account, input.billId)
    return { result: 'OK' }
  }
}
```

`PaymentHandlerService` берёт на себя создание счёта, зачисление, бонусы и запись в историю. От вашего кода нужны только ссылка и проверка подлинности уведомления.

Контроллер, модуль и ключи в `envconfig` добавляются по образцу соседей. Не забудьте про `requireSecrets` в конце `envconfig.ts`: тогда провайдер, включённый без ключей, честно уронит старт вместо тихой поломки оплаты.
