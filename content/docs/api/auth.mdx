Пользователь входит по паре токенов: короткий access и длинный refresh. Сроки задаёте в `.env` (`JWT_EXPIRES`, `JWT_REFRESH_EXPIRES`).

## Вход

```http
POST /auth/login
Content-Type: application/json

{
  "username_or_email": "Notch",
  "password": "…",
  "totp": "123456"
}
```

`totp` нужен только тем, у кого включена двухфакторка. Поле для входа одно, в него подойдёт и ник, и почта.

Ответ:

```json
{
  "accessToken": "eyJ…",
  "refreshToken": "eyJ…",
  "user": { "uuid": "…", "username": "Notch", "real": 0, "virtual": 0 }
}
```

Вместе с ответом сервер ставит две куки: `unicore_refresh` с refresh-токеном (`HttpOnly`, поэтому из JavaScript её не прочитать) и `unicore_csrf` — обычную, читаемую. Браузерным клиентам достаточно кук: сайты хранят access-токен только в памяти вкладки и ничего не кладут в `localStorage`, чтобы XSS не уносил сессию целиком.

Поле `refreshToken` в теле остаётся для клиентов без кук — лаунчеров, плагинов, мобильных приложений.

<Callout type="warn" title="reCAPTCHA">
Если в `.env` заполнены ключи reCAPTCHA, заголовок `recaptcha` с токеном придётся слать при входе, регистрации, сбросе пароля и активации подарка. Действия называются `login`, `register`, `reset`, `verify`, `gift`. Имя действия указывают при генерации токена на клиенте.
</Callout>

## Регистрация

```http
POST /auth/register

{
  "username": "Notch",
  "email": "notch@example.com",
  "password": "…",
  "ref": "PriglashayushiyNick"
}
```

`ref` необязателен, это ник пригласившего для реферальной программы.

Ограничение: 5 регистраций в час с адреса. У ника своё правило: латиница, цифры и `_`, то есть всё, что примет Minecraft.

Пароль проверяется по правилам NIST 800-63B: от 8 до 128 символов, без требований вроде «обязательный спецсимвол», зато с отсевом заведомо слабого. Не пройдут пароли из списка частых (в том числе записанные через `4` вместо `a` и с мусором по краям), повторы одного куска, буквенные и клавиатурные последовательности, а также содержащие ник, почту владельца или название сайта.

Отдельно пароль сверяется с базой утечек Have I Been Pwned — это переключатель **Проверять пароли по базе утечек** в настройках сайта, по умолчанию включённый. Сверка идёт по k-анонимности: наружу уходят первые пять символов SHA-1, сам пароль не передаётся. Если сервис недоступен, пароль принимается — иначе чужой даунтайм останавливал бы регистрацию.

Если в настройках сайта включено подтверждение почты, аккаунт создастся неактивированным и на почту уйдёт код.

## Обновление токена

```http
POST /auth/refresh

{ "refresh_token": "eyJ…" }
```

Возвращает новую пару. Refresh-токен по умолчанию ротируется, старый становится недействительным. Если запросы идут параллельно, обновляйте токен один раз и ждите общего результата, иначе вторая попытка предъявит уже сожжённый токен.

Во фронте так и сделано, несколько ответов `401` ждут одного обновления.

Тело с `refresh_token` нужно только клиентам без кук. Если в запросе пришла кука `unicore_refresh`, сервер берёт токен из неё и игнорирует тело, но требует заголовок `X-CSRF-Token`, равный значению куки `unicore_csrf`. Без совпадения — `403`. Так чужой сайт не сможет обновить сессию за пользователя, хотя браузер и приложит куки к запросу.

## Текущий пользователь

```http
GET /auth/me
Authorization: Bearer <accessToken>
```

Ручка работает и для неактивированных аккаунтов, чтобы сайт показал экран «подтвердите почту», а не выкинул на логин.

## Сессии

Каждый refresh-токен — это сессия с устройством и IP. Их видно в кабинете:

| Метод | Путь | Что делает |
| --- | --- | --- |
| `POST` | `/auth/sessions/me` | Список сессий, текущая помечена |
| `DELETE` | `/auth/sessions/:id` | Закрыть одну |
| `DELETE` | `/auth/sessions_other` | Закрыть все, кроме текущей |
| `DELETE` | `/auth/sessions_all` | Закрыть все |

При входе с незнакомого устройства приходит письмо с IP. Отключить это нечем.

## Активация почты

| Метод | Путь | Что делает |
| --- | --- | --- |
| `POST` | `/auth/verify` | Подтвердить код из письма |
| `GET` | `/auth/resend` | Выслать код заново, 3 раза за 10 минут |

Код перебором не подобрать, попыток всего 10 за 10 минут.

## Сброс пароля

```http
POST /auth/reset      { "email": "notch@example.com" }
POST /auth/password   { "hash": "…", "password": "…" }
```

Первая отправляет письмо со ссылкой, вторая меняет пароль по хешу из этой ссылки. Лимит здесь тот же, 5 запросов в час с адреса.

У второй ручки есть флаг `close`: он заодно закроет все сессии пользователя. Пригодится, когда пароль меняют из-за угона.

<Callout type="error" title="Опять `TRUST_PROXY`">
Все лимиты в этом разделе считаются по IP клиента. За прокси без настроенного `TRUST_PROXY` они схлопываются в один общий счётчик, и первый же пользователь исчерпает лимит на всех.
</Callout>

## Двухфакторная аутентификация

TOTP, подойдёт любое приложение-аутентификатор.

| Метод | Путь | Что делает |
| --- | --- | --- |
| `GET` | `/cabinet/2fa/generate` | Выдать секрет и QR-код |
| `POST` | `/cabinet/2fa/enable` | Включить, подтвердив кодом |
| `POST` | `/cabinet/2fa/disable` | Выключить |

Секрет хранится в базе зашифрованным, резервных кодов нет. Если игрок потерял телефон, двухфакторку снимает администратор из карточки пользователя.

## Выход

```http
POST /auth/logout

{ "refresh_token": "eyJ…" }
```

Отзывает конкретный refresh-токен. Access-токен так не убрать, он работает, пока не кончится его короткий срок.
