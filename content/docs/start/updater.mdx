Обновление запускается вручную в разделе **Обновления CMS**. Проверка новых релизов сама ничего не устанавливает.

## Подготовка обновления

1. Выберите опубликованный релиз. При первом подключении подтвердите исходную версию сайта по сравнению файлов.
2. Отметьте сервер, клиент или админку. Общие библиотеки добавятся автоматически. Если оставленные части несовместимы с новой версией, установка будет заблокирована.
3. Просмотрите перенос своих изменений. Для каждого файла доступны исходная версия, ваши правки, новая версия и результат переноса. Конфликты нужно разрешить до проверки.
4. Если модуль или тема несовместимы, отмените обновление либо явно выберите их отключение. Файлы и данные расширений сохранятся. Вместе с модулем потребуется отключить зависящие от него модули.
5. Запустите проверку. Установщик соберёт выбранный состав и запустит его с отдельной копией базы и файлов сайта.
6. После успешной проверки нажмите **Установить** и подтвердите действие.

Если исходники и готовая сборка расходятся, установщик отдельно запросит согласие на пересборку. Правки, внесённые прямо в собранные файлы, нужно перенести в исходники перед этим шагом.

На время установки сайт перейдёт в обслуживание. Установщик остановит процессы CMS, создаст окончательную резервную копию, проверит её восстановлением, применит изменения базы и проверит запуск. Затем откроет сайт.

Если установка сорвётся до открытия сайта, установщик вернёт прежнюю версию и при необходимости восстановит базу. После открытия сайта старая база автоматически не восстанавливается: новые платежи и действия должны сохраниться. Незавершённую операцию можно посмотреть через команду `status` независимого установщика.

Изменения файлов или настроек после проверки отменяют её результат. Перед установкой потребуется подготовить и проверить обновление заново.

## Подключение обновлений

При новой установке через штатный Docker Compose, `pnpm start` или `ecosystem.config.js` установщик подключается автоматически. Откройте **Обновления CMS** в админке: после подготовки среды можно выбрать версию и обновиться. Файлы сайта, `.env`, модули и темы переносить не нужно.

При ручной установке на Linux пользователю CMS нужен доступ к Docker. Он используется для сборки и проверки копии сайта; создавать отдельные конфигурации установщика не требуется. Все исходники, сборки, копии базы и кэш остаются на хостинге сайта.

### Существующий сайт

Откройте **Обновления CMS**. Если установщик ещё не подключён, появится мастер:

1. Нажмите **Проверить подключение**. Мастер определит способ запуска и доступ к файлам и Docker.
2. Для стандартного PM2 нажмите **Подключить обновления**. Мастер сохранит параметры процессов, подключит отдельную службу и кратковременно перезапустит только процессы CMS.
3. Если сайт запущен отдельной командой, перейдите на показанный мастером штатный запуск. Для существующего Docker-контейнера мастер покажет одну команду подключения службы на хосте.
4. После подключения выберите исходный релиз, просмотрите сравнение файлов и подтвердите версию. Свои изменения сохраняются для последующего переноса.

Подключение доступно сотрудникам с отдельным правом **Подключение установщика обновлений**. Просмотр, подготовка, установка и восстановление имеют собственные права.

Если хостинг не предоставляет доступ к Docker или управлению процессами, подключить службу должен его администратор. Веб-приложению Docker-сокет не передаётся. После подключения дальнейшие обновления выполняются из админки.

## Нестандартное размещение

Установщик работает отдельным процессом на том же Linux-хосте и продолжает работу при остановке CMS. Для нестандартной схемы доступны конфигурация `workspaces/updater/config.example.json` и команда `node workspaces/updater/src/cli.mjs setup /путь/к/config.json`. Это дополнительный способ настройки; штатной установке он не нужен.

Образец уже содержит официальный открытый ключ `unicore-2026-10`. Его PEM-файл: [compat/release-signing-public.pem](https://github.com/MCXTeam/UnicoreCMS/blob/main/compat/release-signing-public.pem). Закрытый ключ на сайт не копируется.

### Docker

В `deployment` задайте `type: "docker"`, имя контейнера и его сетевые параметры в `arguments`. Постоянные данные монтируются отдельно от кода. При установке создаётся новый контейнер с подготовленной версией; прежний сохраняется для восстановления.

Если установщик запущен в контейнере, пути в его конфигурации должны быть доступны Docker-демону под теми же абсолютными именами. Адреса `health` должны вести к процессам CMS из окружения установщика. Для Docker Desktop дополнительно задайте `dockerBackingPath` к диску хранения Docker.

### PM2

```json
{
  "type": "pm2",
  "apps": ["unicore-server", "unicore-client", "unicore-admin"],
  "launcher": "/srv/unicore/updater/launcher.json"
}
```

Поля выше заменяют объект `deployment`. Перед запуском процессов задайте:

```bash
export UNICORE_UPDATER_LAUNCHER=/srv/unicore/updater/runtime/src/launcher.mjs
export UNICORE_UPDATER_LAUNCHER_CONFIG=/srv/unicore/updater/launcher.json
pm2 start ecosystem.config.js
```

Для уже работающих процессов сначала сохраните конфигурацию PM2 и переведите только три процесса CMS на этот launcher. Он читает текущий путь к коду при каждом запуске. Сам установщик запускается отдельно от этих трёх процессов.

### Pterodactyl

```json
{
  "type": "pterodactyl",
  "url": "https://panel.example.org",
  "server": "идентификатор-сервера",
  "token": "Client API token",
  "sameHost": true,
  "launcher": "/srv/unicore/updater/launcher.json",
  "pathMap": {
    "host": "/srv/unicore",
    "container": "/home/container/unicore"
  }
}
```

Установщик должен работать на том же узле с доступом к файлам CMS и Docker. Каталоги кода, данных и установщика должны быть смонтированы в контейнер сервера; `pathMap` описывает соответствие путей. В конфигурации `launcher` указывается путь на узле, а в команде запуска сервера используются пути внутри контейнера:

```bash
node /home/container/unicore/updater/runtime/src/start-all.mjs /home/container/unicore/updater/launcher.json
```

Адаптер проверяет команду запуска в панели до установки и использует Client API для остановки и запуска именно этого сервера. Токену нужен доступ к состоянию, чтению команды запуска и управлению питанием. Он хранится в закрытой конфигурации установщика.

## Состояние и восстановление

```bash
node /srv/unicore/updater/runtime/src/cli.mjs status /srv/unicore/updater/config.json
node /srv/unicore/updater/runtime/src/cli.mjs recover /srv/unicore/updater/config.json ID_ОПЕРАЦИИ
```

Восстановление до открытия сайта возвращает прежнюю установку. Если сайт уже открывался, команда не восстановит старую базу. Сначала проверьте текущее состояние и сохраните новые данные.

Обычные резервные копии хостинга нужны независимо от обновлений. Сохраняйте базу, `.env`, `storage`, модули и темы; ключ шифрования храните с отдельными правами доступа.
